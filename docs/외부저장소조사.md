# 외부 저장소 조사 — 우리가 가져올 것

사용자가 지목한 네 저장소를 훑고, **우리 대시보드에 쓸 만한 것**만 골라 적용 순서를 정한다.

조사일: 2026-09-01

---

## 먼저, 이 조사의 한계

**소스 파일을 한 줄씩 읽지는 않았다.** README·디렉터리 구조·커밋 메시지를 읽었다.
네 저장소를 합치면 수십만 줄이고, 그중 우리가 쓸 수 있는 부분은 처음부터 아주 좁기
때문이다(아래에서 왜인지 설명한다).

그런데 **커밋 메시지가 뜻밖에 값어치가 컸다.** TradingAgents 는 "무엇을 고쳤나"가 아니라
"어떤 함정에 빠졌었나"를 적는 저장소다. 그 함정 목록이 우리가 앞으로 밟을 지뢰밭과
거의 겹친다 — 아래 B 절이 전부 거기서 나왔다.

**그리고 남의 저장소보다 우리 코드를 더 많이 읽었다.** 처음 쓴 초안에는 "우리도 이게
없다"가 넷 있었는데, 확인해 보니 **둘은 이미 되어 있었다**(구조화 출력, LLM 재시도).
그 둘을 지우고 왜 착각했는지를 대신 적어 뒀다 — 다음에 또 조사하지 않도록.

실제로 코드를 가져다 붙이는 일은 없다. **가져오는 것은 설계와 교훈이지 코드가 아니다.**
(라이선스도 그래서 문제되지 않는다. 참고로 TradingAgents Apache-2.0, ccxt MIT,
nautilus_trader LGPL-3.0, lumibot GPL 계열.)

## 네 저장소와 우리 사이의 거리

우리 프로젝트는 **읽기 전용 정보 대시보드**다. CLAUDE.md 절대 규칙 2 가 계좌·자산·주문
API 를 금지한다. 이 선을 기준으로 보면 네 저장소는 두 무리로 갈린다.

| 저장소 | 무엇인가 | 우리와의 거리 |
| --- | --- | --- |
| **TradingAgents** | LLM 여러 개가 역할을 나눠 종목을 분석하는 프레임워크 (LangGraph) | **가깝다.** 우리 서술 분석과 하는 일이 같다 |
| **lumibot** | 파이썬 알고리즘 트레이딩 + 백테스트 + 실제 브로커 주문 | **일부만.** SEC 공시·FRED 매크로 다루는 부분만 |
| **nautilus_trader** | Rust 로 짠 고성능 트레이딩 엔진, 결정론적 이벤트 구동 | **멀다.** 주문 체결·백테스트 엔진이 본체 |
| **ccxt** | 암호화폐 거래소 100곳을 하나의 API 로 묶은 것 | **멀다.** 암호화폐도 안 하고 주문도 안 한다 |

세 번째·네 번째는 **가져올 것이 없다.** 이유는 5절에 적었다.

## A. TradingAgents 에서 가져올 것 — 분석의 짜임

우리 서술 분석(`services/dart_analysis.py`, `services/tenk_analysis.py`)은 지금
**한 번의 LLM 호출로 다섯 필드를 뽑는다.** TradingAgents 는 같은 일을 이렇게 나눈다.

```
애널리스트 4명   기본적(재무) · 뉴스 · 심리(소셜) · 기술적
       ↓
연구원 2명       강세론자 vs 약세론자 — 구조화된 토론
       ↓
트레이더 1명     종합해서 결정
       ↓
리스크팀 + 포트폴리오 매니저   승인/거부
```

뒤쪽 절반(트레이더·리스크·포트폴리오)은 **주문을 내기 위한 것**이라 우리 범위 밖이다.
앞쪽 절반에서 다섯 가지를 따져 봤고, **그중 셋이 남았다**(A-1·A-2·A-4). 나머지 둘은
이미 우리가 하고 있었다.

### A-1. 강세/약세를 나눠서 쓰게 한다 ★ 추천

지금 우리 분석은 한 목소리로 "이 회사는 이렇다"고 말한다. TradingAgents 는 **같은 자료를
놓고 강세론자와 약세론자가 각각 쓰게** 한다.

이게 우리 철학과 맞는다 — 기획서와 CLAUDE.md 가 일관되게 "자료를 보여주고 판단은 사람이
한다"고 못 박아 왔다. 한 목소리 요약은 사람의 판단을 대신하려 들지만, **양쪽을 나란히
놓으면 판단할 재료가 된다.**

- 비용: 호출이 1회 → 2회. 문서당 200~340원 → 400~680원. 하루 상한 20건은 그대로 두고
  건수로 세면 된다.
- 화면: 상세의 `공시·분석` 섹션에 "강세 논거 / 약세 논거" 두 칸.
- 주의: **토론(debate) 라운드까지 흉내내지 않는다.** TradingAgents 는 라운드를 돌며
  서로 반박하는데, 라운드마다 호출이 곱절로 늘고 우리가 얻는 것은 적다.

### A-2. 숫자를 스냅샷에 묶는다 (grounding) ★ 추천 · 싸다

TradingAgents v0.4.0 이 고친 것 중 하나가 이것이다 —
*"the market analyst grounds exact price and indicator claims in a verified data snapshot.
Earlier reports of fabricated price levels across runs are addressed."*

우리 절대 규칙 3 이 "숫자는 LLM 에게 시키지 않는다"인데, **지금은 프롬프트에서 숫자를
빼는 방식으로만 지키고 있다.** 더 나은 방법은 **우리가 계산한 숫자표를 프롬프트에 같이
넣고, 서술이 그 표와 어긋나면 안 된다고 못 박는 것**이다. 지금은 LLM 이 원문에서 본
숫자를 서술에 섞어도 막을 방법이 없다.

- 넣을 것: 그 종목의 재무 요약(매출·영업이익·순이익 3~5년)과 밸류에이션 — 이미 DB 에 있다.
- 비용: 입력 토큰만 조금 는다. 별도 호출 없음.

### A-3. 구조화 출력 — **우리는 이미 하고 있다** (가져올 것 없음)

처음에는 "TradingAgents 가 v0.2.4 에서 구조화 출력으로 옮겼으니 우리도 하자"고 적었다가,
코드를 열어 보고 지웠다. `services/tenk_analysis.py:321` 이 이미 이렇게 부른다:

```python
response = await client.messages.parse(
    ..., output_format=TenKAnalysisContent,
)
```

`messages.parse()` 는 Anthropic SDK 가 권하는 구조화 출력 방식이고, 응답을 스키마로 검증해
준다. 국내(`dart_analysis.py`)도 같다. **이 항목은 이미 끝나 있었다.**

덧붙여, "구조화 출력을 넣었으니 effort 를 낮춰 비용을 아끼자"는 것도 **이미 시험해 보고
되돌린 기록이 있다** — `tenk_analysis.py:48` 주석:

> v2: effort 를 medium → high 로 올렸다. medium 에서 MSFT 가 business_summary 만 채우고
> (…) Sonnet 5 는 낮은 effort 에서 시킨 만큼만 하고 더 파고들지 않는 성향이 있다.

같은 실패를 두 번 하지 않도록 여기 적어 둔다.

### A-4. 회고 — 메모를 쓴 뒤 주가가 어떻게 됐나 ★★ 가장 추천

TradingAgents 의 decision log 는 이렇게 돈다: 결정을 기록해 두고, **다음 실행 때 그 사이의
실현 수익률(원수익률과 SPY 대비 알파)을 가져와** 한 문단 회고를 붙인 뒤 다음 판단에 넣는다.

우리에게는 **메모**가 있다. 기획서가 "이 프로젝트의 차별점"이라 부른 그것이다. 지금 메모는
쓴 시각만 남는다. 여기에 붙일 수 있는 것:

> 2026-05-12 에 쓴 메모 · 그 뒤 **+18.4%** (같은 기간 KOSPI +3.1%)

- **돈이 한 푼도 안 든다.** 확정 종가가 이미 우리 DB 에 있고, 지수도 매크로에 있다.
- LLM 도 안 쓴다. 순수 계산이라 절대 규칙 3 에도 걸리지 않는다.
- 시간이 갈수록 값어치가 커지는 종류의 기능이다 — 판단의 기록이 성적표가 된다.

이게 네 저장소를 통틀어 **우리에게 가장 잘 맞는 아이디어**다.

### A-5. 재시도 — 절반은 이미 되어 있다

TradingAgents 는 `llm_max_retries` 를 둬서 *"a 429 burst can't abort a run"* 하게 했다.
우리는 어떤가 — 확인해 보니 **Anthropic SDK 가 기본으로 2회 자동 재시도한다.**
408·409·429·5xx·연결 오류에 지수 백오프로 붙는다(`max_retries` 기본값 2). 우리 코드는
`AsyncAnthropic(api_key=...)` 로만 만들므로 그 기본값을 그대로 쓰고 있다.

그래서 남은 빈틈은 셋뿐이고, 처음 생각보다 훨씬 작다.

1. **코드만 봐서는 모른다.** 재시도가 있다는 사실이 어디에도 안 적혀 있어서, 다음에
   이 코드를 여는 사람이 (오늘의 나처럼) "재시도가 없네" 하고 또 조사하게 된다.
   `max_retries=` 를 명시하면 값과 의도가 같이 남는다.
2. **2회가 적을 수 있다.** 1~3분짜리 작업이고 건당 200~340원이 걸려 있다.
3. **DART·SEC 원문 받는 쪽에는 재시도가 없다.** LLM 을 부르기 *전에* 원문을 받아 오는데,
   거기서 실패하면 분석 자체가 시작을 못 한다. SEC 는 초당 상한이 빡빡해서 429 가 실제로 난다.

## B. 데이터 정확성 — 커밋 메시지에서 건진 지뢰 목록

여기가 이번 조사의 진짜 수확이다. 아래는 전부 TradingAgents 가 **실제로 겪고 고친** 버그이고,
우리 구조에도 같은 함정이 있다.

### B-1. 당일 캐시와 과거 캐시는 다른 물건이다 (지금은 괜찮다 · 규칙만 남긴다)

> *"the per-day cache was reused unconditionally, so a run started before the day's bar was
> final served that snapshot to every later run, feeding a stale close into technical analysis.
> A present row is not sufficient either, since Yahoo publishes a partial intraday candle;
> a TTL now governs every current-day cache while historical caches stay immutable."*

**우리 실태를 먼저 확인했다.** 처음에는 "우리도 같은 모양"이라고 적었는데, 열어 보니
그렇게 나쁘지 않았다:

| 곳 | 지금 | 판정 |
| --- | --- | --- |
| `services/flows.py` | 5거래일 롤링 창을 300초 TTL | 오늘 것을 영구 보관하지 않는다 — **괜찮다** |
| `services/watchlist.py` | 미국 기준가 300초 TTL | 같은 이유로 괜찮다 |
| `services/macro.py` | 빠른 것 10초 / 느린 것 6시간 | 느린 쪽(기준금리 등)이 6시간이면 타당 |
| `services/valuation.py` | 자체 캐시 없음 (폴러 스냅샷을 읽는다) | 해당 없음 |

**그러니 이 항목은 "고쳐야 한다"가 아니라 "앞으로 밟지 말아야 할 함정"이다.** 지금 캐시는
전부 짧은 TTL 이라 안전한데, 그건 우연에 가깝다 — 규칙으로 적힌 곳이 없기 때문이다.
앞으로 **날짜를 키로 캐시하는 것**(예: 종목별 일봉, 분기 재무)을 새로 만들 때 걸린다.

할 일: 캐시를 새로 만들 때의 규칙 한 줄을 어딘가에 못 박는다 —
**"오늘 날짜가 키에 들어가면 TTL 을 준다. 과거 날짜만 불변으로 캐시한다."**

### B-2. 신선도 가드 — 옛 자료를 새 자료인 척 쓰지 않는다 ★ 급함

> *"yfinance intermittently returns a year-old partial frame that still has rows and a Close,
> so it passed the empty-check and silently fed a wrong close price into the report.
> Add a freshness guard that rejects a frame whose latest row is far older than the requested
> date... the agent reports the specific reason rather than fabricating a value."*

비어 있는지만 보는 검사는 **비어 있지 않은 틀린 값**을 못 잡는다. 우리 `clients/toss.py`,
`clients/krx.py`, `clients/sec.py` 가 받은 응답의 날짜를 요청한 날짜와 대조하고 있는지
확인해야 한다. `/api/health/detail` 의 "장중인데 갱신이 없다" 점검은 있지만 그건 사후
관찰이고, 이건 **응답 하나하나를 문 앞에서 막는** 것이다.

이 프로젝트가 이미 지키는 원칙과 같은 방향이다 — "현재가를 못 받았을 때 확정 종가를 슬쩍
끼워 넣으면 다른 시점의 숫자를 현재가로 착각하게 된다. 비워 두는 편이 정직하다"
(`StockTable.tsx` 주석).

### B-3. 예외는 원인이 아니라 **반응**의 수만큼 만든다

> *"Every condition where a vendor cannot return usable data now derives from a single
> VendorError base: NoMarketDataError, VendorRateLimitError, VendorNotConfiguredError...
> The number of error types tracks the number of distinct router reactions, not the number
> of causes."*

우리는 지금 클라이언트마다 예외가 하나씩이다 — `TossError` `DartError` `SecError` `KrxError`
`FredError` `MacroFeedError`. 전부 그냥 `Exception` 이고 **서로 아무 관계가 없다.** 그래서
라우터가 "429 니까 기다렸다 다시" 와 "그 종목은 원래 없다" 와 "키가 없다" 를 구분하지 못한다.

할 일: 공통 base 를 두고 그 아래 **세 가지 반응**으로 나눈다. 클라이언트별 예외는 그것을
상속만 하면 되므로 기존 코드가 거의 안 바뀐다.

### B-4. 곁가지 자료는 실패해도 화면을 죽이지 않는다

> *"Optional enrichment vendors (FRED macro) raised on a missing key or a network blip,
> which aborted the whole run. Mark macro_data optional; a sole-vendor failure returns a
> sentinel instead of re-raising."*

우리 매크로 띠(FRED·ECOS)가 정확히 그 위치다. 지금 실패하면 어떻게 되는지 확인해야 한다.
시세는 핵심이고 매크로는 곁가지다 — **둘의 실패가 같은 무게면 안 된다.**

### B-5. 시간대와 경계

> *"flat epoch timestamps were parsed in host-local time and offset-aware stamps had tzinfo
> stripped without converting, making filtering machine-dependent. Normalize every operand
> to UTC and use a half-open [start, end + 1 day)."*

우리는 **KST 와 ET 가 한 화면에 섞이는** 앱이다(국내 장·미국 장·SEC·DART). 개발 PC 는
KST, 배포 서버는 UTC 다. 날짜 경계 처리가 기계마다 다르면 "어제 공시"가 서버와 집에서
다르게 나온다. 한 번 훑어볼 값어치가 있다.

## C. lumibot 에서 가져올 것

lumibot 의 본체(브로커 주문·백테스트·AI 매매 에이전트)는 우리 범위 밖이다. 다만 디렉터리
둘이 우리와 같은 자료를 다룬다.

### C-1. FRED 는 값을 **고친다** (`lumibot/macro`, "Fix live FRED realtime date clamp")

FRED 의 realtime 개념 — 같은 날짜의 지표라도 **언제 물어보느냐에 따라 값이 다르다.**
처음 발표된 값과 나중에 개정된 값이 다르기 때문이다. 우리 매크로 띠는 "지금 값"만
보여주므로 당장은 문제가 아니지만, **과거 시점을 보여주는 화면을 만들면 그때 걸린다.**
지금은 알아 두기만 한다.

### C-2. 지표 캐시 설계 (`lumibot/indicators`, `docs/INDICATORS_ARCHITECTURE.md`)

캐시 의미·현재봉 슬라이싱·"이전 봉은 일부러 안 만든다"까지 설계 판단을 문서로 남겨 놨다.
**우리가 기술지표(이동평균·RSI)를 넣게 되면** 그때 읽을 문서다. 지금은 필요 없다.

## D. nautilus_trader · ccxt — 가져올 것 없음

분명히 적어 둔다. "혹시 나중에" 하고 남겨 두면 다음에 또 조사하게 된다.

**nautilus_trader** 는 Rust 로 짠 주문 체결 엔진이다. 결정론적 이벤트 구동, 나노초 단위
시각, Redis 상태 저장 — 전부 **주문을 정확히 내기 위한** 장치다. 우리는 주문을 내지 않는다
(절대 규칙 2). 어댑터 패턴 정도가 눈에 띄지만 우리 벤더는 네 개뿐이라 추상화가 오히려 짐이다.

**ccxt** 는 암호화폐 거래소 100곳을 통합 API 로 묶은 것이다. 우리는 KRX 와 미국 주식만
다루고 암호화폐를 하지 않는다. 거래소마다 다른 응답을 하나로 정규화하는 솜씨는 훌륭하지만,
**정규화할 거래소가 없으면 배울 것도 없다.**

둘 다 규모가 우리와 다르다. 1 OCPU·1GB 서버에서 도는 읽기 전용 대시보드에 트레이딩 엔진의
구조를 들이면 얻는 것보다 잃는 것이 많다.

## 적용 계획

새 라이브러리는 **하나도 필요 없다.** 전부 우리 코드 안에서 끝난다.

### 1단계 — 데이터 정확성 점검 (반나절) ← 여기부터

돈도 안 들고 화면도 안 바뀌지만, **틀린 숫자를 보여주는 것보다 나쁜 것은 없다.**
B 절 다섯 가지를 우리 코드에 대조한다. 고칠 것이 없으면 없다고 적고 넘어간다.

1. **클라이언트 응답 신선도 가드** (B-2) — 다섯 중 이게 가장 값어치 있다
2. 예외 계층 정리 — 반응 세 가지로 (B-3)
3. 매크로 실패가 화면을 죽이는지 확인 (B-4)
4. KST/ET/UTC 경계 훑기 (B-5)
5. 캐시 규칙 한 줄 못 박기 (B-1) — 지금 코드는 괜찮으니 규칙만 남긴다

**확인 방법**: 각각에 회귀 테스트를 붙인다. 우리 테스트 340개는 "실제로 겪은 버그를
회귀로" 쌓아 온 것인데, 이번엔 **남이 겪은 버그를 미리** 넣는 셈이다.

### 2단계 — 메모 회고 (반나절) ★ 가장 값어치 있음

A-4. 메모에 "그 뒤 얼마나 올랐나"를 붙인다. LLM 도 돈도 안 쓴다.

- 백엔드: 메모의 `created_at` 과 종목으로 그 사이 수익률 계산. 지수 대비도 같이.
- 화면: 메모 줄에 한 조각 추가. `+18.4% (KOSPI +3.1%)`
- 주의: 메모를 쓴 날이 휴장일이면 직전 거래일 종가를 쓴다. 종목이 상장폐지됐으면 표시하지 않는다.

### 3단계 — 분석 프롬프트에 숫자 묶기 (2~3시간)

A-2. 우리가 계산한 재무표를 프롬프트에 같이 넣고 서술이 어긋나지 않게 한다.
입력 토큰만 조금 늘고 별도 호출이 없어 **거의 공짜**다.

### 4단계 — 재시도 명시 (1시간)

A-5. `max_retries` 를 명시해 값과 의도를 코드에 남기고, DART·SEC 원문 받는 쪽에 재시도를
붙인다. **구조화 출력은 이미 되어 있으므로 할 일이 없다**(A-3).

### 5단계 — 강세/약세 두 관점 (하루) ← 결정 필요

A-1. **비용이 두 배가 되므로 사용자 확인을 받고 시작한다.**
문서당 200~340원 → 400~680원. 하루 상한 20건은 그대로.

## 결정이 필요한 것

**5단계(강세/약세)를 할 것인가.** 나머지 넷은 돈이 안 들거나 오히려 아끼는 쪽이라
확인 없이 진행해도 되지만, 이건 분석 한 건의 비용이 곱절이 된다.

- 하는 쪽: 한 목소리 요약보다 판단 재료가 된다. 우리 프로젝트 철학과 맞는다.
- 안 하는 쪽: 지금 분석도 이미 사업/위험/경영진단을 나눠 보여준다. 위험요인 항목이
  약세 논거 노릇을 어느 정도 하고 있다.
